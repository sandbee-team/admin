# Security boundaries

## Identity and permissions

Admin staff have their own collection, password hashes, OTP challenges and sessions. There is no public signup. The CLI creates a single initial owner. Owner invitation adds an authorized email; the invited person completes email verification and sets a password through the first-access/recovery screen. Staff records are not Store identities.

Scrypt uses N=32768, r=8, p=1 and per-password random salt. Passwords are 14–128 characters. Login verifies the password first, then a second factor: the authenticator for staff who enrolled one (no email is sent), otherwise an email OTP. Six-digit email codes are HMAC-protected, expire after 10 minutes, allow at most five tries and are consumed transactionally. Recovery relies on mailbox control and revokes old sessions. Email OTP is not phishing-resistant authentication; workforce OIDC/passkeys should be added before exposing high-impact automated deployment execution.

### Authenticator (TOTP), step-up and backup codes

Any staff member may enrol an authenticator app (RFC 6238, SHA-1, 6 digits, 30 seconds, one step of drift). Once enabled it is required at every sign-in and it replaces the email code there: after the password is accepted, `POST /auth/login` sends no email and returns `{totpRequired, challengeId}`, and no session or cookie exists until `POST /auth/verify-totp` succeeds (password plus authenticator is still two factors; the audit row says "Password and authenticator", or "Password and backup code"). Staff without an authenticator still sign in with password and email code, and password recovery still uses the email code. The authenticator challenge lasts five minutes, allows five tries, is single use and is rejected by `/auth/verify`; an email-code challenge is likewise rejected by `/auth/verify-totp`. Password recovery follows the same path: the new password hash is parked in the TOTP challenge and applied only after the authenticator step passes, so an email-only attacker cannot reset the password of an enrolled account. Owner enrolment is effectively mandatory: every owner-only secret route needs step-up and step-up needs TOTP. Sign-in is not blocked for owners who have not enrolled, so bootstrap and recovery keep working; the console shows a banner until they enrol.

Keys are 20 random bytes, stored only as AES-256-GCM boxes bound to the staff record (`staff:<id>:totp`, pending key `staff:<id>:totp-pending`) under VAULT_KEY. The key, QR code and backup codes are returned once, in a `no-store` response. First enrolment needs a session at most 15 minutes old. Replacing a working authenticator needs step-up, a code from the OLD authenticator (or an unused backup code) and the new code in the same request. Confirming enrolment is one transaction: it stores the key, ten backup-code hashes and the matched time step, signs out the member's other sessions, steps up the current session and writes the audit event. A confirmation code must be used within 10 minutes of starting.

Each accepted authenticator code is single use across sign-in and step-up: the matched time step is claimed with an atomic conditional update on `totp.lastStep`, so concurrent requests with the same code produce exactly one success. Backup codes are ten random 10-character codes (shown `XXXXX-XXXXX`). Only HMAC-SHA-256 hashes are stored, keyed from VAULT_KEY with a separate subkey so a lost AUTH_SECRET never touches them; each is removed atomically on use. Only FAILED second-factor attempts count: 10 per 15 minutes (a success gives its slot back). The slot is reserved before the code is checked and given back in the same window row it came from, so each bucket's limit is exact. Inside a session (step-up, enrolment) the limit is per account; before a session exists (sign-in, recovery) it is per account and client address, so someone holding only the password cannot use up the member's step-up budget. Wrong authenticator codes from every path feed the 24 hour counter below, and the code claim refuses once a lock has committed. Residual: a burst sent right at the 20th failure can still evaluate up to the auth gate's concurrent requests (8), so a correct code inside that burst may win (about 20-27 guesses per lock cycle); backup codes are not affected. A correct code seen again in the same 30 second step (double submit, two devices) is answered 400, audited as `totp.replayed` and is not a failure: it feeds neither the lock nor the notice. The per-address bucket relies on the client address: if admin is ever put behind Cloudflare's proxy, TRUST_PROXY_HOPS (trusted proxies) must be updated, or the bucket collapses to the edge addresses. When a password-only sign-in fails at the authenticator step (wrong code or wrong backup code) the member gets a best-effort notice, at most once per 6 hours, and the audit row says `login (password)`. Wrong 6-digit authenticator codes also feed a 24 hour counter; the 20th wrong code within 24 hours locks the authenticator-code path for that account for 24 hours from that code (a rolling lock, `totpLockedUntil`) in every place it is used (sign-in, step-up, enrolment confirmation) and answers 429 "Too many wrong authenticator codes. Use a backup code or ask for a reset." Backup codes keep working because their ~49 bits cannot be brute forced, so a mailbox-only attacker cannot lock the owner out; `reset-totp` clears the lock. Every failed attempt is audited as `totp.failed` (detail login, step-up or enrol; never the code) and the lock itself once as `totp.locked`. Verification (decrypting, checking the step or hash) and failure accounting run outside the sign-in transaction, while the single-use claims (`lastStep`, backup-code removal) run inside the same transaction that consumes the challenge and creates the session, so an aborted sign-in releases the code.

Step-up (`POST /auth/step-up` with an authenticator or backup code) marks the current session as confirmed for 10 minutes (`stepUpUntil` on the session row, so logout and revocation end it). Routes that disclose or destroy secrets use the order authenticate, authorize the role, then require step-up. A missing or expired confirmation answers **428**, not 401: the session is valid and the browser prompts for a code and retries instead of signing out. Regenerating backup codes, replacing or disabling the authenticator also need step-up. Owners cannot disable it (409).

A lost authenticator and lost backup codes are fixed on the server, inside the container (no host Node or `.env` needed; the environment comes from compose `env_file`), from `~/admin` with the API stopped: `docker compose -f compose.production.yaml stop app && docker compose -f compose.production.yaml run --rm app node scripts/recovery.js reset-totp --email=<owner email> --maintenance && docker compose -f compose.production.yaml start app` (see docs/DEPLOYMENT.md). It removes the authenticator state, increments authVersion, deletes the member's sessions and records `totp.reset` (actor System). The member signs in with password and email code, then enrols again. This command does not need BACKUP_KEY.

Key copies: VAULT_KEY should exist in three places (server `.env`, password manager, offline sealed copy), never beside database dumps. `verify-key --kind=vault|backup --copy=server|password-manager|offline`, run in the container (`docker compose -f compose.production.yaml exec app node scripts/recovery.js verify-key ...`, with `exec -T` when piping the key; exact commands in docs/DEPLOYMENT.md), proves a copy by decrypting the database's vault verifier (or comparing fingerprints for BACKUP_KEY). The key is read only from hidden input or stdin (`--key=` is refused), is never logged, stored or sent to the browser, and a mismatch is audited without key material. Only the fingerprint, HMAC-SHA-256 keyed by the key over a fixed label, first 16 hex characters, is stored or shown; it is one-way and is not a prefix of the key. The Recovery page shows when each copy was last verified and the restore-drill age (green up to 100 days, amber up to 190, red after). Audit rows for new events also record the client IP (address characters only, else `invalid`) and a sanitised user agent (control, line-separator and bidi characters removed, 200 characters). They are returned only to staff with the `team` permission (owner), in /audit and the dashboard activity feed; the IP is only as trustworthy as TRUST_PROXY_HOPS.

Best-effort notification emails (never blocking sign-in, never containing codes or keys) go to the affected member when an authenticator is enabled, replaced, turned off or reset, when authenticator codes are locked, and after a password recovery. A mail failure never changes the result of the request. There is a window between deploying this feature and the owner enrolling in which the owner account is protected by password and email code only: enrol immediately after deploy (the console shows a banner until then). The app shell is served with `Cache-Control: no-store` so the browser back/forward cache cannot restore one-time setup data, which the account page also clears on pagehide.

Sessions use random 256-bit tokens stored only as hashes, expire in eight hours, and are limited to five per account. Production cookies use __Host-, Secure, HttpOnly and SameSite=Strict. Every browser mutation checks exact Origin, JSON content type and a session CSRF token. Role/status/authVersion are read from Mongo for each request; mutation transactions recheck authorization against the staff record. Owner cannot be demoted/disabled by API. Read-only staff cannot mutate data; Operations cannot alter catalog, credentials or staff.

## Secrets and audit

Provider credentials use AES-256-GCM with a random IV and record-bound authenticated context. VAULT_KEY is required in the server environment, never sent to browsers, and never included in snapshots. Startup verifies the key against a persistent encrypted verifier. Never casually regenerate this key: old credentials would be lost. A coordinated key-rotation migration is future work; credential replacement is available now.

No connection-credential API returns plaintext or encrypted material: even Admin/Owner can only replace/remove a stored credential. Client account and POS secrets are different: the owner reveal routes return a value only after step-up, are audited and are rate-limited. A future provider worker must be a narrow server-side consumer with explicit permissions, redacted logs and allowlisted provider endpoints. Notes/source URLs must not contain secrets. There are no outbound fetches to user-entered URLs, avoiding a generic SSRF proxy.

Accepted operational mutations and audit events share a Mongo transaction. Audit events contain action, actor, record ID, timestamp and a small fixed description; no provider secret, OTP, password, Mongo URI or request body. Application audit is append-only through API, not cryptographically immutable against a DB administrator. Protect and back up DB access separately.

## Vault, files and POS secrets

Customer account passwords, authenticator (2FA) keys and backup codes, and the POS block's secrets (Vercel token, Mongo URI, Cloudflare token, image keys, generated secrets, POS admin password) are stored as the same AES-256-GCM boxes, each sealed to its record and field: `account:<customerId>:<accountId>:<field>`, `pos:<installationId>:<field>`, `file:<customerId>:<fileId>`. A box copied to another record or field fails to open. They live inside the customer and installation documents but the generic record API never returns them: list projection and detail/PUT scrubbing drop `accounts`, `files` and `pos`, and a generic PUT only `$set`s its own schema keys, so it cannot overwrite them (both are regression-tested). Each module answers only through a whitelist view (`hasPassword`, `hasTotp`, `codesLeft`, `{set, changedAt}` per POS secret), and writes are write-only: replacing a secret never reads the old one.

Reading a value back is a deliberate, narrow act: the owner role only, with step-up (a fresh authenticator code within 10 minutes), over POST (Origin and CSRF checked), limited to 30 reveals and 60 show-codes per hour per person. Decrypt and audit run in one transaction and the value is sent only after it commits, so no reveal exists without an audit event. "Show code" computes the current authenticator code on the server from the stored key and parameters; the key itself is never revealed. Audit details name only the service, label, field or short id: never a value, a file name or a secret. Admins may create and replace secrets and see flags but cannot read, remove or delete them. Secret strings are never trimmed, and validation messages never echo submitted values. Password and secret input fields have an eye button that shows what was typed; it is a per-field, user-initiated choice that starts hidden and resets when the field closes. It does not reveal stored values (that still needs the owner reveal route above), and copy and cut stay blocked on secret fields even while shown.

Concurrency uses a per-entry `rev` (accounts, POS block) so editing one account never bumps the customer revision or resets an open form; stale writes get 409.

Files: S3 only ever receives ciphertext (`SBF1` + IV + AES-256-GCM + tag, additional data `file:<customerId>:<fileId>`) under an opaque key `files/<customerId>/<fileId>`; the per-file data key is sealed with VAULT_KEY, the SHA-256 of the plaintext is recorded, and file names exist only in Mongo. Uploads are streamed with a hard 20 MB limit taken from Content-Length (required), names are sanitised and extensions allow-listed, and at most two transfers run at once. A download is refused (422, nothing sent) unless the object's magic, GCM tag and plaintext SHA-256 all verify, and it always pins the stored S3 `versionId`; it is sent as `application/octet-stream`, `attachment`, `nosniff`. Delete marks the record first and then adds the S3 delete marker (if that call fails the object simply stays current and restorable; the response says `storageDeleted: false`), and restore claims the entry before copying and commits only with its claim token, so concurrent or interrupted restores cannot leave the record pointing at a noncurrent version; restore is possible for 29 days, after which the bucket lifecycle purges the data and restore answers 410. Admin's IAM user cannot delete versions, so a stolen key cannot destroy data at once. S3 errors never reach responses or logs (a fixed "File storage is unavailable." with an internal code), outbound requests refuse redirects and time out, and credentials come only from the server environment. S3 file content is not part of the Mongo snapshot (the sealed data keys are, and every new box location is verified when a snapshot is made or read); keep the bucket's versioning and lifecycle as your file backup. Known limit: if an S3 PUT times out after S3 actually stored the object, the upload fails but an orphan current object (opaque key, ciphertext only, no metadata) remains, and the lifecycle rule only purges noncurrent versions. "Test storage" lists the `files/` prefix; a periodic check of the bucket listing against customer file records reveals such orphans, which can be deleted by hand.

## Deploy adapters and build cache

- **Tokens.** `POS_GITHUB_SOURCE_TOKEN` (source repo, Contents read) and `POS_GITHUB_BUILDER_TOKEN` (builder repo, Actions read/write, Contents read) must match `github_pat_[A-Za-z0-9_]{50,255}`. An empty token disables that half of the feature (503 `not-configured`); a malformed value stops the boot and the error lists variable names only. The two tokens are never mixed: source calls use the source token, builder calls the builder token. Client Vercel and Cloudflare tokens stay vault-encrypted and are decrypted only where a call is made.
- **Fixed hosts, no redirects.** Provider calls (`backend/lib/provider-http.js`) go only to `api.github.com`, `api.vercel.com` and `api.cloudflare.com/client/v4`; callers pass a path, never a URL, and a path that could change host, dot-segments or an encoded slash are refused. Redirects are never followed (`redirect: "manual"`; any 3xx is an error). The single exception is the GitHub artifact download: the 302 target must be `https`, without credentials or port, on `*.blob.core.windows.net` or `*.actions.githubusercontent.com`, and the second request carries no `Authorization` header. Bodies are capped (2 MB; larger only where a caller asks, never above 8 MB) and every call has a timeout combined with the job's abort signal.
- **No bodies in errors.** A failure becomes a `ProviderError` with a fixed message (`<Provider> request failed (<code>)`) and a code. Response bodies, URLs, tokens and request headers never reach a message, property or log; a provider's own error code is kept only if it matches `^[a-z_]{1,40}$`. Text that may still be shown (a CLI's last stderr line) goes through `redact()`, which removes known secrets (also URL-encoded, JSON-escaped and base64), token shapes, Mongo URIs, private-key blocks and long opaque runs, strips control characters and caps the length. Retries (429/5xx/network) happen only for idempotent calls and honour `Retry-After` up to 30 s.
- **Health probe.** The probe (`pos-health.js`, `safe-https.js`) accepts only a public DNS name (no IP literal, port or `localhost`), resolves it through a guarded lookup that refuses every non-public address (loopback, private, link-local, CGNAT, ULA, documentation, mapped and NAT64 forms), follows no redirect and reads at most 64 KB in 10 s. A host's self-reported tenant label is echoed only if it looks like a label.
- **Build-cache poisoning.** The cache holds compiled output that the worker later deploys with a client's token, so a stolen S3 key with write access to `builds/*` must not be able to plant a build. Each object is AES-256-GCM (`SBB1`) under a random data key that exists only sealed under `VAULT_KEY` (AAD `build:<sha>:<buildKey>`) inside a manifest authenticated with an HMAC under a key derived from `VAULT_KEY`. Every reuse checks the MAC, the key fingerprint, that the manifest matches its path and that the object key lives under the same `builds/<sha>/<buildKey>/` prefix, a clean scan, sizes, the ciphertext and plaintext hashes, and the GCM tag at the end of the stream; plaintext goes to a `.part` file and is renamed only after every check. A failure is quarantined (a delete marker on the manifest, never `DeleteObjectVersion`) and the build is redone once; a manifest sealed under another `VAULT_KEY` is a plain miss. `buildKey` is an HMAC (keyed by `VAULT_KEY`) over the build inputs, so S3 key names cannot confirm a guess about a client's values; manifests record names and keyed hashes, never values, and never a customer, installation or deploy outcome.
- **GitHub holds no AWS credentials.** Only the admin worker writes to S3 (`builds/*` and `files/*` under the admin IAM user). The builder workflow produces an artifact that the worker downloads (digest-checked), scans, seals and stores.
- **Known limits.** The cache depends on the owner's lifecycle rule and IAM policy (`docs/POS-STAGE2-REV2.md` 2.8 and 2.9). A planted ciphertext cannot be authenticated without `VAULT_KEY`, but an attacker with write access can delete or block builds (a rebuild covers this).

## Rollout to all clients (P3)

- **Authority.** Starting or resuming a rollout needs the owner role (`deploy`), a fresh authenticator step-up and, for the start, the typed phrase `deploy all`; the start is also bound to the previewed commit and client order by a digest. The worker then runs the rollout for a long time without a browser, so before EVERY client it re-checks the person whose authority it runs under (staff active, same role and `authVersion` as at start/resume, still allowed to `deploy`): a password reset, "sign out everywhere", a role change or a disabled account stops the rollout (`not-authorized`). The freeze switch, Cancel and the per-client lock stop or narrow it at any time.
- **Same job, same gates.** Each client gets the normal deploy job through the same slot claim as the API (`pos.rev`, `deployLock:false`, free slot), after the same client readiness rule (`shared/rollout.js`); nothing bypasses the deploy worker's own checks (preflight, build integrity, health check with automatic rollback).
- **No secrets.** The rollout row and its views hold ids, slugs, status codes and readiness ids only; the Vercel token is reduced to a presence flag inside MongoDB for every rollout decision, so no secret box is read for it. One row only (D4); Dismiss deletes it; the audit trail keeps every start, resume, cancel, per-client enqueue and the end.

## Usage checks (Phase 2)

- **On demand only.** A check runs only after an owner/admin (`credentials`) presses "Check now" or "Check watched clients"; the API queues one slot per installation (`pos.usage.check`) inside a transaction with `authorizeWrite` and an audit row, refuses while the worker is offline (503) and rate-limits (10 per installation and 6 batches per staff per hour). Nothing is scheduled, so an idle admin makes no outbound calls.
- **Secrets stay in the worker.** The worker decrypts `generated.healthStatsToken`, `mongo.uri`, `vercel.token` and `cloudflare.token` (AAD `pos:<id>:<field>`) only for the probe that needs them. A box that cannot be opened is reported as `secret-unreadable`, never echoed. The stats token is sent only as the `x-stats-token` header, only to `pos.statsHost` (the host it was saved for, written only by the secrets writes and the import, so a config-form host change cannot redirect it, D37), only when the value is header-safe, over the guarded health path (public DNS name, guarded lookup, no redirects, 64 KB, 10 s); the only query a probe may add is a short allowlisted pair (`?stats=1`).
- **No new hosts.** Probes go to `pos.host` (already probed by Stage 2), the client's Atlas cluster (hosts must be `*.mongodb.net`), and the fixed provider bases (`api.vercel.com` `/v5/user/tokens/current`; `api.cloudflare.com/client/v4` `tokens/verify` and `/graphql` with a constant query text and inputs only as variables).
- **Untrusted answers.** The cafe's stats body, GraphQL and Vercel bodies are parsed into bounded fields only (cluster names `^[a-z0-9][a-z0-9_-]{0,39}$`, at most 12 clusters, sizes up to 10^12, the fraction recomputed from bytes); provider text never reaches storage. Every stored code comes from `shared/usage-codes.js`.
- **Only the current result is stored** (`pos.usage.last`, overwritten by every check); no probe logs, no history. API views (`backend/lib/usage-view.js`) are whitelists; the lease, attempt and e-mail memory are never returned. The generic records API strips `pos` as before.
- **Email.** One plain-text summary per finished batch to active owners, listing customer name (at most 80 chars), slug, alert title and a short computed detail plus admin links; never a secret, URI, token, header or provider text. De-duplicated per client per alert type for 24 hours (one warning→critical escalation allowed); an SMTP failure never fails a check.

## Sales documents (D52)

- **Who.** Deals, quotations, agreements, invoices, downloads and e-mail need `sales` (owner, admin). The company profile, bank/UPI details, numbering, texts, logo/signature, a client's own quotation or invoice terms (they print beside the payment details) and cancelling a document need `billing` (owner) plus a fresh authenticator step-up, because changed payment instructions on an invoice are a classic payment-redirection fraud. Every write re-checks the staff row inside its transaction (`authorizeWrite`) and writes its audit row in the same transaction. Accepted risk: deal notes and line descriptions (free text by `sales`) also print on documents; every quotation and invoice therefore ends with a fixed line "Pay only to the account above. Our bank details never change by e-mail or phone." that no text can replace.
- **Immutable documents.** An issued document holds a frozen snapshot of everything it prints and the SHA-256 of its PDF. No route changes the snapshot; a revision is a new version (quotation, agreement) and a tax invoice is never re-issued (cancel + next number). Numbers come from a counter incremented inside the issue transaction, so they are unique and gapless per type and financial year (the three prefixes must differ), and a stale `rev` (double click, second tab) is refused.
- **Storage.** The PDF is sealed into S3 exactly like an uploaded customer file (SBF1, per-file key under VAULT_KEY, AAD `file:<customerId>:<fileId>`); a download serves it only after the magic, GCM tag, plaintext SHA-256 and the hash recorded at issue all match, else it re-renders from the snapshot and audits `sales.integrity-failed` (or `sales.archive-unavailable` when S3 is down). A cancelled document downloads only re-rendered with a CANCELLED watermark and is never e-mailed or archived again. Logo and signature bytes are stored in Mongo by hash, kept while the settings or an issued document refer to them, and parsed by a strict PNG/JPEG reader (size, dimensions and decompressed size bounded) before use.
- **PDF writer.** No third-party PDF code: text is WinAnsi-encoded with every delimiter escaped, so user text cannot inject PDF operators; characters the fonts cannot print are refused on save.
- **E-mail.** Only on request, only the current issued version (status and access re-checked right before sending), to at most three addresses typed by staff, plain text plus the PDF, rate-limited (20/hour/person, 5/hour/document); SMTP errors never reach responses or logs. Audit details carry a short deal id, type, number and recipient count, never titles, addresses, amounts or bank data (`/audit` is readable by every role).

## New client go-live (P5 Stage 3, D41-D48, D55, D56)

- **Who.** Start (and "Run all steps again"), Sync env, Update realtime Worker and Unlock and deploy need `deploy` (owner), a fresh authenticator step-up and the typed installation slug; Check DNS needs `credentials` (owner, admin); Cancel needs `deploy`. Per installation: 10 runs and 30 DNS checks per hour; Unlock and deploy shares the deploy allowance (30/h). Every enqueue is one transaction with `authorizeWrite`, the `pos.rev` guard, free deploy/task/go-live slots and its audit row. A go-live run and a deploy, task or POS setup write never overlap (D41, both ways).
- **Provider writes admin now makes (D42, amends D25).** Only inside a go-live, only in the client's own accounts with the client's own vault tokens, and only while the Vercel project has no production deployment (a live project is an existing client: `project-live`, refused). Vercel: create the project (name, framework, root directory, Function Region `bom1`) or adopt it by name, then `PATCH` Node `22.x` and `sourceFilesOutsideRootDirectory` (only when different); upsert exactly the `buildEnv` keys (D43); add and verify the domain `<label>.sandbee.in`; set 308 redirects of the project's `*.vercel.app` names to it. Cloudflare (only with realtime on): register a workers.dev subdomain only when the account has none, upload the Worker `pos-realtime-<slug>` (bundle, `TENANT_ID`, publish secret), enable its workers.dev route. GitHub (builder repo, builder token): dispatch `realtime.yml`, delete its artifact after reading it. Client database: one insert-only upsert of a `role: "admin"` staff document when none exists; an existing admin is never changed (`admin-exists`); no index is created. **Nothing is deleted** — no project, Worker, domain, env variable, DNS record or client document — and admin never writes DNS (the owner enters the records at GoDaddy by hand, D40). After go-live the project settings are never changed again; the env changes only through the owner's Sync env.
- **What is stored: keyed fingerprints, never values.** The secrets a go-live mints (`authSecret`, `healthStatsToken`, `realtimePublishSecret`, and the POS admin password when the owner set none) are vault boxes `pos:<id>:<field>` like every POS secret, minted once and never re-minted; the POS admin password reaches the owner only through the existing reveal (owner, step-up, audited). For the env, `pos.golive.env.keys` keeps per key only the name, type, targets, Vercel's `updatedAt` and `fp16` = the first 16 hex of HMAC(HMAC(VAULT_KEY, `sandbee-env-fp-v1`), JSON `[key, value]`); Vercel env values are never stored — plain values are fingerprinted in memory and dropped, encrypted ones are never read. For the POS admin login it keeps the username and keyed fingerprints (same key) of the password and the Mongo URI it was made with, never the values. Being keyed, a stolen database dump cannot confirm a guessed value without VAULT_KEY. `fp16`, the username and the fingerprints never leave the server (no view returns them).
- **POS admin seed.** `bcryptjs` exactly 2.4.3 (the POS's own library; pure JavaScript, no install script), used only by `backend/lib/pos-admin-seed.js`: cost 12, the POS seed script's password rule, one atomic upsert keyed on the role (two seeds at once leave one admin), then a read-back `compare` proves the stored hash opens with the vault password. A change of the POS `Staff` schema fails loudly (`admin-seed-failed`), never silently.
- **Network.** Provider calls keep the fixed hosts, no-redirect rule and error hygiene of the deploy adapters above (multipart uploads ≤ 2 MiB, built in memory). The DNS check asks sandbee.in's own authoritative nameservers directly (≤ 8 addresses, UDP/TCP 53) about the one label; an unknown answer is `dns-unreachable`, never "free". The TLS probe and the health check of `<label>.sandbee.in` use the guarded `safe-https` path; realtime probes go only to the `https://*.workers.dev` URL of the Worker admin uploaded (`GET /join` expecting 426, and one signed publish with at most 3 allowed headers and 4 KB).
- **Untrusted realtime bundle.** Accepted only from a `realtime.yml` run on the builder's `main`, event `workflow_dispatch`, with the expected run-name, exactly one digest-carrying `pos-realtime-<id>` artifact, a zip of exactly `index.js` (≤ 1 MiB) and `realtime.json` (≤ 16 KB), a descriptor inside the allowlist (one Durable Object binding, `new_sqlite_classes` migrations only, no compatibility flags) and a matching SHA-256 and size. GitHub holds no Cloudflare credential: the workflow bundles with the pinned wrangler's `--dry-run` only.
- **Audit and logs.** Audit details carry ids, step names, counts and codes only (`pos.golive.*`, `pos.unlocked`, `pos.verify.completed`); never a token, URI, password, env value or provider text.
- **Known limits.** Admin now writes into client Vercel projects and client databases (accepted, D42/D45, bounded as above). A client Cloudflare token with "All accounts" or "All zones" scope could reach sandbee.in once P4 moves its DNS: ask every client for a token scoped to its own account. A concurrent POS setup save on another installation and a Start with the same label can both commit (the unique label index and the DNS check catch it before anything goes live).

## Availability and load

JSON requests are bounded at 32 KB (the two POS import routes and the three sales text PUTs, settings, client profile and deal, allow 128 KB). Lists are paginated at 30 items; option pickers are capped at 100 with search. Field lengths, lifecycle values, identifiers and extra properties are validated with shared strict schemas. Connection pools are capped; common summary data uses a local LRU with five-second TTL and invalidation on local writes. Authorization never uses this cache. Another replica may show a summary up to five seconds old.

Mongo fixed-window rate counters are shared across replicas. API: 400/IP/minute. Login: 20/IP and 6/email/15 minutes. Recovery: 10/IP and 3/email/15 minutes. Verification: 40/IP/15 minutes, plus five attempts/challenge. A process admits up to eight concurrent authentication requests. Window boundaries can allow short bursts; put an edge/WAF limit in front of the admin origin. TRUST_PROXY_HOPS must exactly match the trusted reverse-proxy topology; never enable arbitrary proxy trust.

No unlimited-traffic or zero-bug guarantee. This is a staff control plane, not an API traffic gateway. Monitor latency, pool wait time, DB capacity, audit growth and 429/5xx rates. Keep an explicit audit retention/export policy as usage grows. All admin write replicas must pause during the small-installation snapshot tool.

## Store bridge

STORE_MONGODB_URI is optional and must use a Mongo read-only account in production. Only counts and recent workspace ID/name/creation date are selected. The connection is never used to mutate Store. Direct reads intentionally do not return sessions, tokens, licenses or password hashes. Schema coupling is documented; replace it with a versioned internal Store API before enabling admin write actions.

## Deployment defaults

Local Compose has unauthenticated Mongo on loopback and a private Docker network only; never deploy this development stack publicly. Production Compose uses your authenticated external Mongo replica set/Atlas, HTTPS reverse proxy, secure SMTP, non-root runtime, read-only filesystem and dropped capabilities. Restrict admin access by network/Cloudflare Access where practical. Update dependencies and test backups regularly.
