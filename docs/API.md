# Internal Admin API

This same-origin API is for the internal console, not customer integrations. All routes are under `/api`. Successful responses are JSON. Errors are `{error, requestId}`. Never authenticate Admin with a Store/customer API key.

Stale-revision 409s (an edit based on an out-of-date `revision` or `rev`, or a file claimed by another restore) add a machine-readable `code`: `{error, code: "stale", requestId}`; clients reload on `code === "stale"` instead of matching the message. File routes answer `code: "not-configured"` (503) when S3 is not set up. Every other error keeps `{error, requestId}`.

Status 428 means the action needs a fresh authenticator confirmation (`POST /auth/step-up`) and the session is still valid; only 401 ends a session. Browser mutation requirements: exact APP_URL Origin, application/json, HTTP-only session cookie and X-CSRF-Token from `/auth/me` or `/auth/verify`. Login/recovery/OTP verification have no session yet and require Origin/JSON plus strict rate limiting.

Per-staff hourly limits: file upload 60, file download 60, storage self-test 10, secret reveal 30, show-code 60. `GET /overview` returns `latestRecovery` as `{restoredAt}` only (the latest restore drill date), never a full row.

Account, file and POS responses never contain secrets except the deliberate reveal, show-code and download responses. Customer and installation `GET`/`PUT` never include `accounts`, `files` or `pos`. Every mutation (including DELETE and bodyless POST) must send a JSON body, `{}` at minimum, except the raw upload. File routes answer 503 "File storage is not configured." until the `FILES_S3_*` variables are set.

List parameters: page (1–10000, 30 records/page), search (max 100 chars), status, customerId, productId (installation filter), model (product delivery-model filter). Sort is updatedAt then ID descending. Option lists cap at 100 and accept search/customerId. No unbounded export route exists. Search regex is escaped and timed; high-volume text search should move to an indexed search strategy if customer registry size demands it.

The shared `schemas.js` is the source of truth for payloads. Unknown body properties are rejected. Unique identity conflicts and stale revisions return 409. Wrong permissions return 403; invalid/expired sessions 401; validation 400; limits 429; database/mail outages 503 or a sanitized 500. Request IDs support incident correlation without logging payload secrets.

Allowed installation transitions: planned → ready/retired; ready → planned/live/retired; live → paused/retired; paused → live/retired. Retired is terminal. New installations always start planned. Ready/live states validate the product-specific preparation checklist, required providers and source/version where required. Live requires every check for that delivery model and verification evidence; hosted models additionally require an endpoint. Local packages do not require a public endpoint. Product identifiers are immutable, and delivery model/provider requirements cannot change while non-retired installations exist. See STORE-UI-UPDATE.md for the model matrix. This is not an execution state machine for automated deployment.

## POS deploys (Stage 2)

The API only **enqueues and reads**; the worker (`backend/worker`, W2) executes. Every route below needs the `pos` product (400 otherwise) and a session. Gates follow D28: `deploy` is owner-only; step-up means a fresh authenticator confirmation (428 otherwise); a typed slug means `confirm` must equal `pos.slug` (400 otherwise). Responses are whitelist views (`backend/lib/deploy-view.js`): no lease/fence, run ids, object keys or full build keys. `PUT /installations/:id/pos` no longer accepts `deployLock` (400, strict schema); a new POS block is always locked, and only the unlock route below changes it. While a deploy job is active, config `PUT`, `PUT/DELETE` of `vercel.token` and `mongo.uri`, and `DELETE` of the POS block return 409 `code:"busy"`.

Extra error codes (all `{error, code, requestId}`): 409 `not-ready` also carries `items:[readiness ids]`; 409 `busy`; 409 `branch-moved` (the branch head is now behind the requested sha, so the branch was moved back); 409 `sha-not-on-branch` (sha unknown, diverged, or the branch is gone); 409 `too-late` (cancel after upload started); 409 `cache-off`; 502 `provider-error` (GitHub failed; the message is `GitHub request failed (<code>).`); 503 `builder-unavailable` / `not-configured`.

### Readiness

`readinessOf()` (`shared/deploy.js`) is the only place readiness is computed; the GET and every enqueue gate call it. Item ids: `worker`, `builder`, `source-token`, `build-cache` (amber, never blocks), `authenticator`, `not-frozen`, `vercel-token`, `project-ids`, `verified`, `host`, `image-realtime`, `unlocked`, `customer-active`. Which items block which operation (`GATES`): deploy/redeploy = all required; rollback = worker, authenticator, vercel-token, project-ids, host, unlocked, customer-active; build = worker, builder, source-token, image-realtime; verify = worker; purge = worker, vercel-token, project-ids, unlocked, customer-active; unlock = vercel-token, project-ids, host, verified, customer-active. A blocked gate is 409 `{code:"not-ready", items:[ids]}`.

### Deploy job contract

Stored shapes (MongoDB). The same text lives as a comment block in `shared/deploy.js`; the constants (`DEPLOY_STATES`, `JOB_STEPS`, `LEASE_MS`, and so on) are exported from there for the worker.

**`installations.pos.deploy`** = `{current, last, previous, cutoverAt}`. The worker never changes `pos.rev`.

**`current`** (one slot; `null` when idle; a failed, cancelled, rolled-back, unhealthy or expired job stays until dismissed or replaced):

| --- | --- |
| `kind` | `deploy` \| `redeploy` \| `rollback` |

| `branch`, `sha` | what to ship (40-hex). For a rollback: the target (`previous`) |
| `buildKey` | 64 hex or `null`; the API fills it when the builder descriptor is readable, the worker recomputes it in `resolve` |
| `commit` | `{sha, branch, headline <=120 (first line), authorName (name only, never an e-mail), date}` or `null`. Enqueue = one conditional `updateOne` inside a transaction with `authorizeWrite` and the audit row. It matches only when `pos.deployLock` is false, `pos.rev` is unchanged and `current` is empty, finished, a `queued` job older than 10 minutes, or an active job whose lease has been dead for 15 minutes. Two concurrent requests therefore give one 201 and one 409 `busy`. Claim (worker): filter on `requestId` and (`status:"queued"` or an active status with `lease.until < now`), set `lease.owner`, `lease.until = now + 60 s`, `$inc lease.fence`, `$inc attempt`; heartbeat every 15 s.

**`last` / `previous`** (written by the worker finalize transaction): `{kind, requestId, branch, sha, at, by, vercelDeploymentId, url, durationMs, runUrl, status: succeeded|rolled-back-to|pre-admin, build:{buildKey, objectKey, touchedAt, source: cache|fresh|artifact}, commit:{sha, branch, headline <=120, authorName, date}}`. Views expose `build.key8` and `build.cached` only. `cutoverAt` is the first verified prebuilt deploy.

**`installations.pos.task`** (one slot): `{id, kind: verify|db-backup|purge-preview|purge, status: queued|running|succeeded|failed|cancelled|expired, step, progress, lease, attempt, by, requestedAt, finishedAt, params, result, error}`. `purge.params` = `{ids, digest, previewTaskId}`; `purge-preview.result` = `{at, candidates[<=200 {id, createdAt, target, state}], total, keep}`. **`installations.pos.verify`** = `{at, by, vercel, project, env, mongo, cloudflare, health}`, each `"ok"`, a fixed code or `null` (skipped).

**`system_state` rows**
- `pos-worker`: heartbeat `{at, workerId, version, cliVersion, builderConfigured, builder:{sha, nodeVersion, cliVersion, ok, checkedAt}, lastBuildMs}`; online means `at` is under 90 s old; the builder check is stale after 30 minutes.
- `pos-deploy-freeze`: `{on, reason, by, at}`.
- `pos-build:<sha>:<buildKey>`: transient build row `{kind:"build", status: queued|dispatching|building|collecting|storing|ready|failed|cancelled, sha, buildKey, inputs, branch, commit, lease, attempt, runId, runUrl, artifactId, waiters[<=20 job ids], prepared:{by,at}\|null, error, createdAt, finishedAt}`; the unique `_id` is the single-flight lock. `inputs.env` values are canonical (`new URL(v).href`, lowercase cloud name).
- `pos-retention`: `{status, at, lease, result}` for the daily copy-forward sweep (not enqueued by the API).

Indexes: partial `installations` on `pos.deploy.current.status` and `pos.task.status`; partial `system_state` on `{kind, status}` for build rows.

### Client DB backup

Owner button (D6, D28): backs up a POS client's own MongoDB into the customer's files. Only on the owner's click; nothing is scheduled.

- `POST /api/installations/:id/pos/db-backup` (empty JSON body): `deploy` permission (owner) plus step-up. Answers 201 `{task}`, 409 `busy` (one active task per installation), 409 when no database URI is stored, 429 above 6 per hour per installation, 428 without step-up, 503 `not-configured` when file storage is off.
- `GET /api/installations/:id/pos/db-backup` (`credentials`): `{configured, task}`. `task` = `{id, status: queued|running|succeeded|failed|expired, step, by, requestedAt, finishedAt, progress{collections, documents, bytes}, result{collections, documents, bytes}, error{code, message}}`: counts only, never names, documents or URIs.

The worker streams every non-system collection as canonical EJSON lines (a header with the database name and collection list, one `{"c","d"}` line per document, a trailer with exact counts), gzips them, seals the result like a client file (SBF1, AES-256-GCM, data key under VAULT_KEY) and registers it as category `db-backup`, named `<slug>-db-<yyyymmdd-hhmm>.jsonl.gz`. The limit is 20 MB compressed: above it the run stops, stores nothing and fails with `backup-too-large` (use `mongodump` locally). A backup is not resumable: a worker restart ends it as `backup-failed`. Audit: `pos.db-backup.requested` (API) and `pos.db-backup.created` (worker, size and counts only). Download uses the normal file download (owner, step-up).
